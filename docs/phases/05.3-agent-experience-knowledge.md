# Фаза 5.3. Понятные агенты, база знаний и интеграции

## Цель

Администратор без технической подготовки описывает задачу словами, получает работающего агента, проверяет его на примерах и видит результат в чате. Агенты опираются на базу знаний пространства, умеют опрашивать людей и ждать ответа, а данные из внешних систем подключаются без изменения ядра.

UX-референс — кликабельный прототип [`design/prototypes/agents-lab/index.html`](../../design/prototypes/agents-lab/index.html): каталог, Архитектор, конструктор, сценарии в чатах, активность. Прототип задаёт структуру и формулировки, а не пиксели; вёрстка идёт на токенах и компонентах Interface Lab ([design-system.md](../design-system.md)).

## Исходное состояние (проверено по коду 2026-11-10)

- Весь интерфейс агентов — один файл `apps/web/src/settings/pages/AgentSettingsPage.tsx` (2324 строки). Вкладки карточки режут одну форму; права показаны как 11 scopes; автоматизации — select из 7 типов и текстовое поле «Конфигурация»; вкладка «Знания» — заглушка `AgentKnowledgePlaceholder`.
- Шаблонов три (`summarizer`, `qa`, `onboarding`), промпты зашиты во фронтенд (`templateDescriptions`).
- В чате агент — обычное сообщение с меткой и строка стриминга (`AgentStreamRow`). Нет кнопок в сообщениях, меню команд в композере, источников под ответом. Подтверждения — только в `/agents/approvals`.
- Инструменты агента (`core/internal/agenttool/executor.go`): `get_chat_messages`, `get_thread`, `search_messages`, `post_message`, `reply_in_thread`, `add_reaction`, `get_file_text`, `list_members`, `remember`, `recall`.
- Знания: текст извлекается из `text/*`, DOCX и PDF в `files.extracted_text`, есть FTS по файлам; pgvector установлен, таблицы эмбеддингов есть, генерации нет. Документ существует только как вложение сообщения.
- Интеграции: MCP-серверы привязаны к конкретному агенту (`agent_mcp_servers`, `agentconfig.Service`), общего подключения пространства нет.
- Триггеры: `manual`, `mention`, `command`, `keyword`, `every_message`, `schedule`, `event`. Отложенного запуска «через N часов после события» нет.
- У чатов нет собственной аватарки: в `chats` нет поля, показываются инициалы по `avatar_seed`.

## Вводные первого клиента

Реабилитационный центр: инструкторы, врачи, администраторы. В переписке только организационные вопросы, внешние модели подключаются сразу. Смен нет: администраторы зовут инструкторов на слоты, в течение дня один инструктор сменяет другого. Процесса «заявок» нет. Где ведётся расписание (1С, таблица или чат) — неизвестно; фаза не должна от этого зависеть.

Сценарии пилота: «Контроль» (все ли отметились под сообщением), «Справка» (ответы по регламентам с источником), «Наставник» (новички), «Слоты» (поиск инструктора на слот), «Передача» (дела между слотами), «Что я пропустил» (личная сводка).

## В scope

- база знаний пространства: коллекции, документы и страницы, индексация, поиск, права;
- интерактивные сообщения агента: карточки, кнопки, источники;
- механика «опросить людей и дождаться»: ожидаемые ответы, срок, напоминания, итог;
- отложенный повторный запуск агента;
- новый интерфейс: каталог, конструктор из пяти блоков, проверка, активность;
- агент в чате: меню команд, панель «Агенты в этом чате», подтверждение в карточке;
- Архитектор — агент, который собирает черновик другого агента из разговора;
- интеграции уровня пространства: общие MCP-подключения, входящие вебхуки, табличные источники;
- набор шаблонов пилота и их проверочные примеры;
- собственные аватарки чатов.

## Вне scope

- распознавание сканов (OCR) и синхронизация с внешними дисками;
- готовый коннектор к конкретной версии 1С — только точка расширения и пример адаптера;
- конструктор агентов и база знаний в мобильном клиенте: телефон только отображает карточки и принимает нажатия;
- маркетплейс агентов, платные границы;
- голосовые сообщения и расшифровка звонков.

## Рабочие пакеты

Каждый пакет выполняет отдельный агент в своей ветке от `main` и открывает PR. Пакеты одной волны независимы и идут параллельно. Номера миграций закреплены заранее, чтобы ветки не конфликтовали.

### Волна 1 — основа

**A. База знаний: сервер** · миграция `00044`

- Таблицы `knowledge_collections`, `knowledge_documents` (файл или markdown-страница), `knowledge_chunks` (текст, `tsvector`, `embedding vector`, позиция в документе).
- Индексация задачей River по образцу `file.process`: нарезка на фрагменты, FTS всегда, эмбеддинги — если у подключения пространства задана embedding-модель. Без неё поиск работает по словам.
- Извлечение текста из XLSX и CSV в дополнение к имеющимся форматам.
- Право `knowledge.manage`: по умолчанию у owner и admin, выдаётся участнику. Чтение коллекции — всем участникам либо выбранным чатам.
- API `/api/v1/knowledge/*` в `packages/protocol/openapi.yaml`; коллекции привязываются к версии агента.
- Инструмент `search_knowledge` (scope `knowledge:read`): возвращает фрагменты с документом, заголовком раздела и позицией.
- Приёмка: документ после загрузки находится запросом; агент без привязанной коллекции её не видит; удаление документа убирает фрагменты; участник без права не может загрузить.

**B. Интерактивные сообщения и опросы: сервер** · миграция `00045`

- Сообщение получает необязательные блоки: карточка (заголовок, статус, поля, список), кнопки, источники. Схема версионируется; клиент без поддержки показывает текстовый fallback.
- `POST /messages/{id}/actions/{action_id}` — нажатие кнопки участником; сервер проверяет, кому действие разрешено, обеспечивает идемпотентность и будит run агента событием.
- Сущность «сбор ответов»: целевое сообщение, список ожидаемых участников, способ ответа (реакция, кнопка, текст), срок, расписание напоминаний, получатель итога.
- Отложенный запуск: агент планирует собственное продолжение на момент времени с сохранённым контекстом; учитываются бюджет, пауза и удаление агента.
- Инструменты: `post_card`, `update_card`, `get_reactions`, `start_collection`, `get_collection`, `schedule_followup`, `send_direct_message` (последний — с подтверждением по политике агента).
- Существующие подтверждения tool-вызовов отображаются той же карточкой в чате; раздел `/agents/approvals` остаётся общей очередью.
- Приёмка: кнопку нельзя нажать дважды и нельзя нажать постороннему; в `dry_run` карточки и напоминания не отправляются; отложенный запуск переживает рестарт Core; пауза агента отменяет напоминания.

**C. Аватарки чатов** · миграция `00046`

- `chats.avatar_file_id`, `avatar_version`; `PUT/DELETE /chats/{id}/avatar` по образцу аватара участника; только PNG и JPEG.
- Web: загрузка в окне информации о чате, отображение в списке и шапке. Mobile: отображение.
- Приёмка: менять может владелец и администратор чата; удаление возвращает инициалы.

**D. Web: разбор монолита агентов** · без изменения поведения

- `AgentSettingsPage.tsx` разбирается на модули в `apps/web/src/agents/` (catalog, detail, wizard, sandbox, approvals, activity, connections), i18n — через `defineCatalog`.
- Промпты шаблонов переносятся на сервер как рецепты с локализацией.
- Приёмка: Playwright-сценарии и снимки агентов проходят без обновления эталонов.

### Волна 2 — интерфейс и интеграции

Зависит от A, B и D.

**E. Web: каталог, конструктор, проверка**

- Каталог: карточки с описанием задачи и человеческим статусом, полоса «ждут подтверждения», готовые роли.
- Конструктор — одна страница из блоков «Кто он», «Что знает», «Что умеет», «Когда включается», «Где работает», «Модель и данные». Правила запуска читаются как предложения. Для каждого действия — «сам» или «после подтверждения». Scopes выводятся из блоков 2–3 и видны только в расширенных настройках.
- Проверка справа: готовые примеры рецепта, ответ агента, человеческий trace, стоимость.
- Сохраняются draft/publish/rollback фазы 5.2.
- Приёмка: обычный путь не показывает scopes, лимиты и идентификаторы; агент из шаблона создаётся и публикуется за 3–5 минут; экраны работают на 390 px.

**F. Агент в чате: web и mobile**

- Рендер карточек, кнопок и источников в `MessageRow`; состояние «нажато», «недоступно», «устарело».
- Меню команд в композере по `/` со списком команд агентов текущего чата.
- Панель «Агенты в этом чате»: что агент читает, что может делать, пауза, добавление агента.
- Mobile (`apps/mobile`): карточки, кнопки, источники; без панели управления.
- Приёмка: сценарии «Контроль», «Слоты», «Передача» из прототипа проходят в Playwright на мок-API и в Maestro на симуляторе.

**G. Web: раздел «База знаний»**

- Коллекции, загрузка файлов, страницы в markdown, статус обработки, ошибки извлечения, выдача права `knowledge.manage`.
- Документы базы знаний в общем поиске Coma.
- Блок «Что знает» конструктора выбирает коллекции и документы.

**H. Интеграции пространства** · миграция `00047`

- MCP-подключения поднимаются на уровень пространства (как LLM connections в 5.2): секрет хранится один раз, агентам назначается подключение и разрешённые инструменты. Существующие `agent_mcp_servers` мигрируют.
- Входящий вебхук: внешняя система присылает событие, которое становится триггером агента; подпись запроса, rate limit, журнал.
- Табличный источник: XLSX или CSV из базы знаний доступен инструментом `query_table` (фильтр по столбцам), чтобы расписание из таблицы работало без интеграции.
- Проверка исходящих адресов на SSRF, аудит изменений подключений.
- Документация и пример адаптера в `examples/agents`: MCP-сервер поверх HTTP-API учётной системы («получить слоты», «назначить инструктора»).
- Приёмка: агент «Слоты» работает на табличном источнике и, не меняя рецепта, на примере MCP-адаптера.

### Волна 3 — Архитектор и пилот

Зависит от волны 2.

**I. Архитектор агентов**

- Системный агент с инструментами только над черновиками: `create_draft`, `update_draft`, `list_chats`, `list_knowledge`, `propose_tests`, `run_test`. Публиковать не может.
- Экран: разговор слева, «паспорт агента» справа, заполняется по ходу; результат открывается в конструкторе.
- Архитектор задаёт не больше четырёх уточняющих вопросов и предлагает варианты ответа.
- Вход «Изменить через Архитектора» из конструктора.
- Приёмка: шесть сценариев пилота собираются из одной фразы и уточнений; права черновика не шире описанной задачи; каждый шаг виден в паспорте.

**J. Шаблоны пилота**

- Рецепты «Контроль», «Справка», «Наставник», «Слоты», «Передача», «Что я пропустил» с предметными формами, RU/EN, 3–5 проверочными примерами.
- Seed-пространство для демо и e2e.

**K. Сквозная проверка и документы**

- PostgreSQL E2E полного пути: документ → агент → публикация → вызов в чате → опрос → напоминание → итог.
- Обновление `docs/protocols/agents-v1.md`, руководство администратора по агентам и базе знаний, раздел о том, какие данные уходят во внешнюю модель.
- Пилот в реабилитационном центре, сбор замечаний.

## Правила для исполнителей

- Ветка от актуального `main`, один PR на пакет; слияние выполняет координатор: push в `main` сразу выкатывается на стейджинг.
- Коммиты в стиле conventional commits на английском, без трейлеров атрибуции.
- Контракт сначала: изменение `packages/protocol/openapi.yaml`, затем `make generate`; сгенерированный код коммитится.
- Миграции только вперёд-совместимые, с номером, закреплённым за пакетом.
- Все строки интерфейса — через i18n, RU и EN; `check:i18n` проходит.
- Перед PR: `pnpm lint`, `pnpm test`, `pnpm build`, `gofmt`, `go vet`, `go test ./core/...` на временном Postgres. Существующие compose-проекты и тома на машине не трогать.
- Сервер остаётся источником прав: клиент не решает, кому доступна кнопка или документ.
- `dry_run` не создаёт сообщений, карточек, напоминаний и внешних вызовов записи.
- Вымышленные данные в тестах и демо; реальных данных клиента в репозитории нет.

## Контракты и данные

- Новые scopes: `knowledge:read`, `messages:interactive`, `followups:write`, `tables:read`. Новое право пространства: `knowledge.manage`.
- Блоки сообщения — часть `/api/v1`, изменения только аддитивные; у каждого блока есть текстовый fallback.
- Каждый run сохраняет, какие фрагменты базы знаний были выданы модели: это основа источников и аудита.
- Эмбеддинги документов отправляются во внешнюю модель только при явном согласии на внешнюю передачу данных в подключении.
- Опрос и отложенный запуск привязаны к версии агента; откат версии не отменяет уже начатый опрос, пауза — отменяет напоминания.

## Критерии приёмки фазы

- Администратор без подсказок собирает через Архитектора агента «Контроль» и видит в чате отчёт «кто не отметился».
- «Справка» отвечает по загруженному регламенту с источником и честно сообщает, когда ответа нет.
- «Слоты» опрашивает инструкторов и не меняет расписание без решения администратора.
- Сотрудник с выданным правом загружает документ в базу знаний; без права — не может.
- Все карточки отображаются и нажимаются в web и в мобильном клиенте.
- Обычный путь нигде не показывает scopes, лимиты и технические идентификаторы.

## Риски и открытые вопросы

- Где центр ведёт расписание. До ответа «Слоты» и «Передача» опираются на табличный источник; пакет H оставляет точку подключения.
- Качество самописного извлечения текста из PDF на реальных регламентах не проверено; при плохом результате заменить библиотекой в пакете A.
- Общие инструкции — известная слабость конструкторов «по описанию». Ответ фазы — паспорт агента и обязательная проверка на примерах перед публикацией.
- Архитектор принят основным путём создания агента, конструктор — местом правки. Решение можно пересмотреть после пилота.
- Напоминания в личных сообщениях могут раздражать: нужны тихие часы и предел числа напоминаний на человека.

## Definition of Done

- Пакеты A–K слиты, CI зелёный, стейджинг обновлён.
- Шесть шаблонов пилота работают в реабилитационном центре на внешней модели.
- Протокол агентов и руководство администратора обновлены.
- Замечания пилота разобраны: исправлены либо записаны в план следующей фазы.
