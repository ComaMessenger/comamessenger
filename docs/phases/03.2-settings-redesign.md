# Фаза 3.2. Редизайн и расширение настроек

Статус: в работе с 21 августа 2026 года. Предыдущая фаза — [3.1 Навигация и настройки](03.1-navigation-settings.md).

Место в roadmap: фаза 3.2 выполняется **перед фазой 4**. Она меняет контракты `UserPreferences`, `User`/`Actor`, permissions и реестр настроек, на которые опирается следующий этап, поэтому запускать фазы целиком параллельно нельзя. Исключение — шаг 1 (вынос модуля без изменения поведения), который может идти уже сейчас. Файловое хранилище и аватары сознательно перенесены в фазу 4 и не блокируют этот редизайн.

Текущий прогресс: создан иерархический permission-aware реестр, маршруты настроек генерируются из него, зарегистрирован `/settings/notifications`, а Workspace разделён на прямые вложенные маршруты `/general`, `/members`, `/invitations` и `/policies` с независимой проверкой прав. Все страницы настроек, `SettingsShell`, общие form-примитивы и `useAutosave` с unit-тестами вынесены в `apps/web/src/settings/`; `App.tsx` больше не содержит settings-страниц. Backend загружает effective permissions в identity и возвращает их через `/me`/token responses; OpenAPI, generated Go/TypeScript contracts, workspace/invitation authorization и owner-панель выдачи прав синхронизированы. Миграция `actor_permissions` делает backfill существующих администраторов и обеспечивает DB-инвариант «явные права только у активного admin». Передача ownership реализована отдельным API и owner-only UI с повторной проверкой пароля, атомарной сменой ролей/permissions, аудитом и DB-гарантией единственного активного owner. `chats.moderate` применяется к удалению чужих сообщений, просмотру/изменению состава и архивированию любых групп и каналов даже без membership; chat-owner и topology direct-чатов защищены, административные действия пишутся в аудит. Профиль поддерживает `title`, `about` и явный timezone; должность проходит через directory, chat members и workspace members. `POST /me/password` повторно проверяет текущий пароль, атомарно меняет hash, отзывает все остальные HTTP/realtime-сессии и пишет аудит; Security показывает читаемые названия браузера и ОС. Смена email требует текущий пароль: без SMTP адрес меняется сразу, с SMTP используется хешированный одноразовый токен на один час; подтверждение повторно проверяет уникальность и отзывает остальные HTTP/realtime-сессии. Owner или admin с `members.manage` может потребовать смену пароля участником, не получая reset-токен: сервер отзывает все его сессии, до успешной смены ограничивает HTTP безопасным минимумом и отклоняет realtime с `password_change_required` без reconnect-цикла. Password recovery завершён: публичный endpoint не раскрывает существование аккаунта, SMTP-ссылка и локальная operator-ссылка одноразовые, хранятся только хешем, действуют час и при использовании отзывают все сессии; workspace-администратор никогда не видит токен. Кастомный статус завершён: эмодзи, текст и срок хранятся у актора, истечение очищается серверным worker, а durable realtime-событие обновляет sidebar, каталог участников и заголовок личного чата на всех клиентах. Контракт preferences разделён на полный read-model и частичный update, папки и закрепы вынесены в отдельные endpoints. Snooze с пресетами и произвольным временем действует на всех устройствах; интервалы фиксируются отдельно, поэтому события, подавленные во время паузы, не «догоняют» пользователя после её окончания. Глобальные правила сообщений и тредов, звук и расписание в timezone пользователя применяются в push-материализаторе и редактируются на полноценной странице. Диагностика показывает готовность сервера, browser permission и безопасный список подписок, отправляет тест через реальный web-push transport; chat overrides теперь имеют настоящий inherited `default`, перечисляются отдельно и сбрасываются одним действием. Реакции, добавление в чат, смена роли и удаление из чата проходят через тот же durable notification pipeline с snooze, расписанием, дедупликацией, retry и отдельными category preferences. Email-дайджест использует независимую от Web Push durable-очередь, пакетирует пропущенные события 15 минут, соблюдает privacy preview и не отправляет старые письма после повторного включения SMTP. Следующий срез — завершение управления приглашениями.

Обновление прогресса приглашений: lifecycle завершён — API и UI показывают метаданные без token, поддерживают revoke и атомарную rotate с одноразовым показом новой ссылки, а SMTP-доставка отражается явным результатом. Политика `allow_member_invitations` вычисляется сервером как `User.can_create_invitations`: обычный участник может создать только member-приглашение и не получает доступ к списку или административным действиям. `default_timezone` пространства применяется при принятии приглашения, если пользователь не выбрал timezone. Следующий срез — финальный аудит страниц, audit log и сквозные e2e фазы.

Обновление прогресса audit log: API поддерживает category/actor/date filters и keyset pagination через `after_id`, обогащает событие ролью автора, категорией, именем цели и безопасным `changes`. Страница формирует человекочитаемые RU/EN-предложения для полного текущего каталога административных действий и показывает «было → стало» вместо внутренних action codes. Остался финальный UI/e2e/design-system аудит фазы.

До первого публичного релиза API v1 не гарантирует совместимость с предыдущими development-сборками. Изменения preferences выпускаются атомарно вместе с web-клиентом: поддержка N−1 не требуется, но существующие пользовательские значения в JSONB сохраняются миграциями.

## Цель

Настройки становятся отдельным, масштабируемым модулем с предсказуемым layout, понятной иерархией и достаточным набором опций для реальной команды: у пользователя есть полноценный профиль (должность, «о себе», часовой пояс, email и пароль), у администратора — управление участниками с тремя ролями, читаемый журнал аудита и политики пространства. Код настроек вынесен из `App.tsx` в `apps/web/src/settings/` с реестром секций, чтобы новые страницы добавлялись одним файлом.

## Диагноз текущего состояния

По скринам и коду (`apps/web/src/App.tsx:4336-5770`, `styles.css:2333-2480`):

1. **Двухколоночная «кладка» карточек.** `settings-page__body--columns` раскладывает секции в `grid 2×N`, карточки разной высоты оставляют дыры (профиль: карточка аватара висит в пустоте, «Внешний вид» уезжает под неё, «Аккаунт» растягивается на всю ширину). Нет единой вертикальной оси чтения.
2. **Дублирование заголовков.** Header «Настройки профиля» + вкладка «Профиль» + карточка «Личные настройки» говорят одно и то же. На странице уведомлений текст «Показывать текст сообщения» повторяется три раза (заголовок секции, описание, тогл).
3. **Контролы не из дизайн-системы.** Нативный `checkbox` вместо switch, кнопка «Выйти» растянута на 1500px, color-picker — голый `<input type=color>`, статусная плашка «Уведомления включены» конкурирует с тоглом рядом.
4. **Горизонтальные вкладки не масштабируются.** Семь пунктов уже упираются в ширину; добавление «Участники», «Приглашения», «Интеграции» сделает строку нечитаемой на desktop и вынудит скролл на phone.
5. **Аудит показывает машинные коды** (`organization.settings.update`, `invitation.accept`) и `target_type` на английском; нет «что именно изменилось», нет фильтров и пагинации.
6. **Роли названы «Владелец / Администратор / Участник»**, причём на странице пространства роль выводится сырой строкой (`workspaceRole: "Роль: {role}"` → «Роль: owner»). У участников нет должности, поэтому в списке участников и в карточке профиля нельзя понять, кто есть кто.
7. Маршрут `/settings/notifications` не зарегистрирован в `router.tsx` (работает только потому, что `App` сам матчит `pathname`).

## В scope

- Новый layout настроек: вертикальная навигация слева, одна колонка контента.
- Единые примитивы форм настроек: `SettingsRow`, `Switch`, `SegmentedControl`, `ColorField`, `DangerZone`.
- Профиль: должность, «о себе», часовой пояс, смена email и пароля; до фазы 4 вместо аватара используются инициалы.
- Кастомный статус: эмодзи + текст + срок действия, задаётся в выпадающем меню профиля в sidebar (не на странице настроек), виден в списке участников, в шапке личного чата и рядом с именем.
- Уведомления: детальные правила (сообщения / личные / упоминания / треды / реакции), расписание по дням и времени, звук, «Отключить уведомления» на всех устройствах с пресетами, диагностика и список исключений по чатам, email-дайджест для офлайна (только если SMTP настроен).
- Безопасность: смена пароля, список сессий с устройством, IP и временем активности (без геолокации), выход отовсюду.
- Пространство: разделение на «Общее», «Участники», «Приглашения», «Политики».
- Роли: `owner` → «Главный администратор», `admin` → «Администратор», `member` → «Участник»; передача прав главного администратора.
- Точечные права администраторов: главный администратор включает каждому администратору конкретные разрешения (участники, приглашения, оформление, политики, подключения, аудит, модерация чатов); сервер проверяет именно разрешение, а не роль.
- Должность (`title`) у актора: в профиле, в списке участников, в карточке участника и в popover по клику на имя в чате.
- Аудит: человекочитаемые RU/EN описания с подстановкой значений «было → стало», фильтры по типу/актору/дате, пагинация по курсору.
- Вынос настроек в `apps/web/src/settings/` с реестром секций и отдельными файлами страниц.

## Вне scope

- 2FA/TOTP (v1.1 по `product-spec.md`), OIDC.
- Кастомные именованные роли (наборы прав сохраняются только per-admin; шаблоны ролей — позже).
- Права на уровне отдельного чата или канала сверх существующих chat-ролей.
- Организационная структура (отделы, руководители) — только плоское поле «должность».
- Файловое хранилище и загрузка аватаров: они реализуются в фазе 4 поверх общего `storage.BlobStore` с local filesystem и S3 backend.
- Мобильный нативный клиент (фаза 6); phone-layout делается только для web.
- Геолокация сессий по IP.
- Отложенная доставка уведомлений, подавленных во время snooze.

## Пользовательские сценарии

- Участник открывает настройки и за один экран без скролла видит, где он находится и что можно изменить; все изменения сохраняются автоматически.
- Участник указывает должность «Руководитель отдела продаж» — её видят коллеги в списке участников и по клику на имя в чате; вместо аватара пока показываются инициалы.
- Участник меняет пароль, подтвердив текущий; все остальные сессии завершаются.
- Участник ставит статус «👽 Рисую дизайны» на 2 часа, включает расписание «будни 09:00–19:00» и режим «личные сообщения и упоминания» для всех чатов; уходя на встречу, выбирает «Отключить уведомления → на 1 час» — тишина на всех устройствах.
- Главный администратор назначает второго администратора, меняет должности участников, деактивирует ушедшего сотрудника и передаёт права главного администратора.
- Администратор видит в аудите: «Лев Павлов изменил название пространства: «Coma» → «Coma Team»» и может отфильтровать только события участников за неделю.

## Принцип: всё работает без SMTP

Coma — self-hosted продукт, и подключение почты необязательно. Ни один сценарий этой фазы не должен быть заблокирован отсутствием SMTP; почта — только дополнительный канал. Для каждого сценария, где обычно используется письмо, есть режим без почты:

| Сценарий                      | С SMTP                                                                         | Без SMTP                                                                                                                                                               |
| ----------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Приглашение                   | Ссылка показана один раз + письмо адресату                                     | Ссылка показана один раз (как сейчас)                                                                                                                                  |
| Сброс пароля участнику        | Одноразовая ссылка уходит только на email участника, администратор её не видит | Workspace owner/admin может только потребовать смену известного пароля; при полностью забытом пароле локальный оператор сервера выпускает одноразовую ссылку через CLI |
| Забыл пароль (сам)            | Форма «Забыли пароль?» отправляет письмо                                       | Форма показывает «Обратитесь к администратору пространства», без утечки, существует ли адрес                                                                           |
| Смена своего email            | Ссылка-подтверждение на новый адрес, уведомление на старый                     | Меняется сразу после ввода текущего пароля; `email_verified_at` сбрасывается; запись в аудите и на странице «Безопасность»                                             |
| Смена пароля                  | Уведомление на email                                                           | Без уведомления; событие видно в списке сессий/«Безопасность»                                                                                                          |
| Email-дайджест уведомлений    | Доступен                                                                       | Секция не показывается                                                                                                                                                 |
| Изменение прав/роли участника | Письмо-уведомление                                                             | Системное уведомление внутри Coma (`notify_system`)                                                                                                                    |

Режим без SMTP сохраняет границу между администратором пространства и оператором сервера. `owner` и admin с `members.manage` могут выставить `must_change_password`, если участник помнит старый пароль, но не получают reset-токен и не могут войти под участником. Если пароль полностью забыт, интерфейс направляет к оператору инсталляции. Оператор запускает локальную команду `comamessenger admin issue-password-reset --email user@example.com` (в Compose — `docker compose --env-file .env -f deploy/compose.yaml run --rm --no-deps core admin issue-password-reset --email user@example.com`); команда недоступна по публичному HTTP API, печатает одноразовую ссылку с TTL 1 час в терминал и пишет аудит `member.password_reset.issue` с `delivery: operator`. Инфраструктурный оператор и так контролирует процесс и БД, но передача workspace ownership через UI не передаёт способность impersonation.

Системные уведомления внутри Coma (`notify_system`) становятся основным каналом для событий аккаунта: смена роли, выдача прав, сброс пароля, смена email, новая сессия.

- **Desktop (≥ 1024px):** левая навигация 232px внутри рабочей области, сгруппированная (`Личное` / `Пространство`), без верхнего дублирующего header. - Группы и блоки внутри страницы — `SettingsGroup` (заголовок h2 + подпись) с одной карточкой, внутри карточки — `SettingsRow`: слева label + hint, справа контрол фиксированной ширины (инпут 280px, switch, select). Строки разделены hairline. Это убирает «кладку» и дублирование заголовков.
- Деструктивные действия собраны в `DangerZone` в конце страницы, кнопки компактные, не на всю ширину.
- Тогглы — `Switch` из дизайн-системы; бинарные выборы из 2–3 значений — `SegmentedControl` (тема: Системная / Светлая / Тёмная).
- Страница пространства разбивается: «Общее» (название, slug, часовой пояс по умолчанию), «Участники» (таблица), «Приглашения» (политика + список активных ссылок), «Политики» (кто создаёт чаты/каналы, кто приглашает).

Изменения фиксируются в `docs/design-system.md` (раздел «Settings layout»), включая правило: **в настройках нет многоколоночных сеток карточек**.

### Роли и точечные права

| Роль (код) | RU                    | EN     | Права                                                                                                             |
| ---------- | --------------------- | ------ | ----------------------------------------------------------------------------------------------------------------- |
| `owner`    | Главный администратор | Owner  | Все права без ограничений; единственный, кто назначает администраторов, настраивает их права и передаёт свою роль |
| `admin`    | Администратор         | Admin  | Личные настройки + тот набор прав, который ему выдал главный администратор                                        |
| `member`   | Участник              | Member | Только личные настройки                                                                                           |

Коды ролей в БД и API не меняются. Вместо «admin может всё, кроме owner» вводится набор разрешений, который хранится у каждого администратора отдельно.

**Каталог разрешений** (`core/internal/permission/permission.go`, единый источник правды для сервера; OpenAPI enum и i18n синхронизируются с ним):

| Код                   | RU                     | Что открывает                                                                                                                                                              |
| --------------------- | ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `members.manage`      | Участники              | Должности, деактивация и реактивация участников (только `member`)                                                                                                          |
| `invitations.manage`  | Приглашения            | Создание и отзыв приглашений, политика приглашений                                                                                                                         |
| `workspace.settings`  | Настройки пространства | Название, slug, часовой пояс по умолчанию                                                                                                                                  |
| `workspace.policies`  | Политики               | Кто создаёт чаты/каналы, кто приглашает                                                                                                                                    |
| `branding.manage`     | Оформление             | Логотип, favicon, акцентный цвет                                                                                                                                           |
| `integrations.manage` | Подключения            | S3/SMTP configuration и тест соединения (секреты по-прежнему не возвращаются)                                                                                              |
| `audit.read`          | Аудит                  | Просмотр журнала аудита                                                                                                                                                    |
| `chats.moderate`      | Модерация чатов        | Удаление чужих сообщений, архивирование групп/каналов и управление их non-owner участниками без обязательного membership; topology direct-чатов и chat-owner не изменяются |

Правила:

- `owner` неявно имеет все разрешения; список для него не редактируется. Owner-only операций две: назначение/снятие `admin` и их прав, передача роли. Всё остальное, включая инфраструктуру (`integrations.manage`), делегируемо — но `integrations.manage` и `workspace.policies` не входят в пресет по умолчанию и выдаются осознанно.
- Назначить роль `admin`, изменить его набор прав, снять роль — может только `owner`. Администратор с `members.manage` управляет только участниками с ролью `member`.
- При назначении `admin` по умолчанию включается пресет «Базовый администратор» (`members.manage`, `invitations.manage`, `branding.manage`, `audit.read`); остальное включается вручную.
- Сервер проверяет разрешение через `authz.Require(user, permission)`; проверка «по роли» остаётся только для `owner`-only операций (передача роли, управление admin).
- Навигация и контролы в настройках строятся от `user.permissions` из `/me`, а не от `user.role`: администратор без `integrations.manage` не видит «Подключения».
- Любое изменение прав пишет аудит `organization.member.permissions.update` с `changes: {permissions: {from: [...], to: [...]}}` → «Лев Павлов выдал Гульфине права: Подключения, Аудит».

Хранение: отдельная таблица `actor_permissions(org_id, actor_id, permission, granted_by, granted_at)` с `PRIMARY KEY(org_id, actor_id, permission)` и составными foreign keys в рамках организации. У `owner` права не хранятся — он получает каталог неявно; строки допустимы только для активного `admin`. При смене роли на `member`/`owner` или деактивации разрешения удаляются в той же транзакции; удаление actor каскадно очищает их. Runtime дополнительно применяет stored permissions только к роли `admin`, поэтому ошибочная строка в БД не повышает участника. `granted_by/granted_at` сохраняют происхождение выдачи прав.

UI: в таблице участников у администратора появляется кнопка «Права» → боковая панель со списком switch по каталогу, группировка по разделам настроек, пресет «Базовый администратор» одной кнопкой, автосохранение как у остальных настроек.

Передача роли главного администратора — отдельная операция `POST /organization/transfer-ownership` с подтверждением паролем. Операция атомарно меняет роли, удаляет stored permissions нового owner, выдаёт бывшему owner полный admin-набор и пишет аудит `organization.ownership.transfer`. Обычный `PATCH /organization/members/{id}` не принимает роль `owner`; частичный unique index допускает ровно одного активного owner на организацию, а существующий deferred constraint не допускает ни одного. Локальный operator recovery не связан с workspace ownership.

### Должность

Должность — **свободное текстовое поле**, не связанное с ролью: роль (`owner/admin/member`) определяет права, должность («Руководитель отдела продаж», «Дизайнер») — только подпись, которую видят коллеги. `actors.title text CHECK (length(title) <= 80)`, nullable. Редактирует сам пользователь, а также owner или admin с `members.manage` (через «Участники»). Показывается: карточка профиля, список участников (`/members`), строка участника в настройках, popover актора в чате, результаты поиска людей.

### Кастомный статус

Как в Slack/Pachca: пользователь задаёт эмодзи + короткий текст («👽 Рисую дизайны», «🏖 В отпуске до 3 сентября») и срок действия (30 минут / 1 час / сегодня / неделя / не сбрасывать / своя дата). По истечении статус очищается сервером.

- Данные: `actors.status_emoji text`, `actors.status_text text CHECK (length <= 100)`, `actors.status_expires_at timestamptz`. Отдаётся в `User`, `OrganizationMember`, `Actor` (для списков и popover) и в realtime-событии `actor.status.updated`, чтобы коллеги видели смену без перезагрузки.
- API: `PUT /me/status`, `DELETE /me/status`. Пресеты статусов («На встрече», «В отпуске», «Работаю удалённо», «Болею») — клиентские, редактируются свободно.
- UI: статус задаётся **только** в выпадающем меню профиля (клик по своему имени в sidebar): первой строкой — поле «Чем заняты?» с кнопкой эмодзи слева, кнопкой очистки справа и выбором срока действия; ниже — пресеты статусов. На странице «Профиль» статус не редактируется и не показывается как поле (там только постоянные данные: имя и должность). Эмодзи статуса отображается рядом с именем в sidebar, списке участников, шапке личного чата, popover актора.
- Не смешивается с присутствием (`online/away/offline`) — присутствие вычисляется автоматически, статус задаётся вручную.

### Отключить уведомления (snooze)

Глобальное «не беспокоить» на **всех устройствах**: хранится на сервере, а не в браузере.

- `users.preferences.snoozed_until timestamptz | null`. Пресеты в меню профиля: 30 минут / 1 час / 2 часа / до завтра (09:00 в TZ пользователя) / свой вариант (дата и время). Там же «Личные настройки» и «Настройки уведомлений» как быстрые ссылки. Durable-интервалы дополнительно записываются в `notification_snoozes`, чтобы событие, созданное во время паузы, оставалось подавленным даже если worker обработает очередь уже после завершения snooze.
- Семантика — обычный DND: уведомления, возникшие во время snooze, **подавляются навсегда**, отложенной доставки нет (она потребовала бы отдельной очереди и планировщика). После окончания периода отправляются только новые события; непрочитанное остаётся видно через счётчики и список «Важные». Push-выборка (`push/service.go`) фильтрует `snoozed_until > now()`; тот же фильтр применяется к звуку и браузерным уведомлениям в открытой вкладке.
- Индикатор: перечёркнутый колокольчик у своего имени в sidebar с tooltip «Уведомления отключены до 14:30», клик — отменить.

### Настройки уведомлений

Страница с тремя вкладками, автосохранение, без кнопок «Отменить/Сохранить»:

**Настройки**

- Сообщения в чатах (radio): все новые сообщения / личные сообщения и упоминания / ничего. Это default для чатов без собственного override.
- Треды, на которые подписан (radio): все ответы / только упоминания / ничего.
- Другие уведомления (switch): реакции на мои сообщения; приглашения в чаты и каналы; системные (смена роли, прав, деактивация).
- Звук: switch + выбор из 3–4 звуков с предпрослушиванием.
- Показывать текст сообщения (существующий `push_preview`).
- Расписание: дни (каждый день / будние / выбрать), время (весь день / в указанный период `from–to` в TZ пользователя). Это заменяет «тихие часы» из первой редакции плана.
- Email-дайджест (только при настроенном SMTP): выкл / раз в час / раз в день, о непрочитанных упоминаниях и личных сообщениях.

**Диагностика**

- Состояние разрешения браузера (`Notification.permission`) и кнопка «Активировать уведомления» (текущий flow `pushManager.subscribe`).
- Список подписанных устройств (из `web_push_subscriptions`: UA, дата) с возможностью отписать.
- «Отправить тестовое уведомление» — `POST /push/test`, проходит весь реальный pipeline.
- Статус service worker и VAPID (`/push/config`), понятные подсказки, если пуши отключены на сервере.

**Исключения**

- Список чатов, у которых `chat_members.notify_level`/`muted_until` отличаются от default, с возможностью сбросить к default прямо из списка. Пустое состояние: «Исключений пока нет. Чтобы добавить чат в исключения, измените настройки уведомлений в самом чате».
- Данные: `GET /chats/notification-overrides` (чаты с не-default настройками), сброс — существующий `PATCH /chats/{id}/notification-preferences`.

Серверная выборка push учитывает, по порядку: `push_enabled` → `snoozed_until` → расписание → override чата → default по типу (личка / упоминание / обычное сообщение / тред / реакция).

### Человекочитаемый аудит

Сервер уже пишет `action`, `target_type`, `metadata`. Добавляем:

- В `metadata` всех административных мутаций — `changes: {field: {from, to}}` (секреты маскируются на сервере: для S3/SMTP — только флаг `credentials_changed`).
- В ответе `/organization/audit` — `actor_name`, `actor_role`, `target_name` (имя участника/чата/организации на момент выборки).
- Клиентский словарь `settings/audit/describe.ts`: `action → (entry, t) => string`. Примеры:
  - `organization.settings.update` → «Лев Павлов изменил настройки пространства: название «Coma» → «Coma Team»»
  - `organization.member.update` (`role`) → «Лев Павлов назначил Гульфину администратором»
  - `organization.member.update` (`status: deactivated`) → «Лев Павлов деактивировал участника Иван Петров»
  - `invitation.create` → «Лев Павлов создал приглашение для a@b.ru с ролью Участник»
  - `invitation.accept` → «Гульфина приняла приглашение и присоединилась к пространству»
  - `organization.branding.update` → «Лев Павлов обновил логотип»
  - `organization.infrastructure.update` → «Лев Павлов изменил настройки SMTP (хост, порт)»
  - `chat.create` → «Лев Павлов создал канал #general»
  - неизвестный action → fallback «Лев Павлов: chat.manage» (чтобы новые серверные события не ломали UI).
- UI: строка = иконка категории + предложение + относительное время; раскрытие показывает таблицу «поле / было / стало». Фильтры: категория (пространство / участники / приглашения / чаты / оформление / подключения), актор, период. Пагинация — `after_id` + `limit`, как у `/actors`.
- Серверный список action остаётся источником правды: `core/internal/workspace/audit_actions.go` с константами, тест проверяет, что для каждой константы есть ключ в RU/EN каталоге.

- `router.tsx` генерирует маршруты из `registry` (исправляет пропуск `/settings/notifications`); `App.tsx` рендерит `<SettingsShell />` по префиксу `/settings`.
- Доступ описывается не ролью, а `access: { permission?, ownerOnly? }`; `canAccess(user, entry)` (owner проходит всегда, иначе проверяется набор разрешений пользователя) используется и навигацией, и `SettingsShell` при прямом переходе по URL — одна функция, два места вызова. Это та же модель, что и серверный `authz.Require`.
- `permissionsOf(user)` использует обязательное generated-поле `User.permissions` без role-fallback. `owner` получает полный effective-каталог на сервере, `member` — непустой JSON-массив нулевой длины, `admin` — только сохранённые коды. Один и тот же реестр управляет видимостью навигации и прямым переходом по URL.
- `useAutosave` получает unit-тесты (debounce, сериализация, stale response) при переносе — сейчас тестируется только через Playwright.
- Критерий шага: бандл и e2e проходят без изменения снапшотов; `App.tsx` уменьшается примерно на 1500 строк.

### 2. Примитивы дизайн-системы

`Switch`, `SegmentedControl`, `SettingsRow`, `SettingsGroup`, `DangerZone`, `ColorField` (swatch + HEX + пресеты). Появляются в `/dev/components` и в `docs/design-system.md`.

### 3. Профиль и аккаунт

- Бэкенд: `actors.title`, `actors.about` (≤ 280); `PATCH /me` принимает `title`, `about`, `timezone`; `POST /me/password` (current + new, инвалидирует другие сессии); смена email с повторной аутентификацией: `POST /me/email/change {new_email, current_password}` проверяет пароль и уникальность адреса в организации (409 `email_taken`). Без SMTP адрес меняется сразу, `email_verified_at` сбрасывается, остальные сессии завершаются, пишется аудит `member.email.change`. С SMTP — двухшаговое подтверждение через `email_change_tokens` (`actor_id, new_email, token_hash, expires_at`, TTL 1 час, `used_at`): ссылка уходит на новый адрес, уведомления — на старый; `POST /me/email/confirm {token}` повторно проверяет уникальность, атомарно меняет адрес и завершает остальные сессии.
- Администратор не вводит чужой пароль и не меняет чужой email. С SMTP admin с `members.manage` может выпустить reset-токен, который отправляется только участнику. Без SMTP workspace-администратор может только «Потребовать смену пароля при следующем входе» (`users.must_change_password_at`), после чего все сессии участника отзываются. Полностью забытый пароль восстанавливает только локальный оператор через `comamessenger admin issue-password-reset`; токен хранится хешем, имеет TTL 1 час и одноразовое использование. Аудит: `member.password_reset.issue` (`delivery: email|operator`) и `member.password_change.require`.
- Фронт: страница по макету выше, часовой пояс выбирается явно (сейчас перезаписывается из браузера при каждом сохранении — это нужно убрать).

### 4. Уведомления, статус, snooze

- `PATCH /preferences` становится частичным. Схемы разделяются: `UserPreferences` — полный объект с обязательными полями для `GET` и ответа `PATCH`; `UpdatePreferencesRequest` — отдельная схема, все поля optional, `additionalProperties: false`, минимум одно поле. Сервер мержит в JSONB (уже `preferences || $3`) и возвращает полный объект, поэтому generated TS-типы для чтения остаются строгими. `chat_folders` и `pinned_chat_ids` выносятся в отдельные `PUT /preferences/chat-folders` и `PUT /preferences/pinned-chats`; `UserPreferences` их больше не содержит. Клиентские папки/закрепы переводятся на новые endpoints.
- Новые поля `preferences`: `notify_messages` (`all|direct_and_mentions|none`), `notify_threads` (`all|mentions|none`), `notify_reactions`, `notify_invites`, `notify_system`, `sound_enabled`, `sound_id`, `schedule {days: all|weekdays|[0-6], from, to}`, `snoozed_until`, `email_digest`.
- Статус: поля в `actors`, `PUT/DELETE /me/status`, realtime-событие, job очистки просроченных статусов.
- Push (`push/service.go:263`): выборка переписывается под цепочку правил выше; `POST /push/test`; `GET /push/subscriptions` для диагностики; `GET /chats/notification-overrides`.
- UI: три вкладки страницы уведомлений, меню профиля со статусом и snooze-пресетами.

### 5. Безопасность

Смена пароля (`POST /me/password`: текущий + новый, завершает остальные сессии), список сессий с парсингом UA в «Chrome · macOS», IP, временем последней активности и пометкой «текущая», выход отовсюду — переоформляется в `SettingsRow`. Геолокация по IP сознательно не делается: это внешний GeoIP-источник, вопросы хранения и приватности; при необходимости — отдельным решением в `docs/decisions/`.

### 6. Пространство и участники

- «Участники»: таблица с поиском, колонки Имя/должность, Роль (select по матрице прав), Статус, Последняя активность; массовых действий нет.
- «Приглашения»: политика (роль по умолчанию, TTL) + список активных приглашений. В БД хранится только `token_hash`, поэтому ссылку повторно показать нельзя и хранить её открытой мы не будем: `GET /invitations` возвращает метаданные (email, роль, кто создал, срок, статус), `DELETE /invitations/{invitation_id}` отзывает, `POST /invitations/{invitation_id}/rotate` отзывает старое и создаёт новое приглашение с новой ссылкой, которая показывается один раз. Если настроен SMTP, при создании/ротации письмо уходит адресату автоматически.
- `organization.settings` расширяется: `default_timezone`, `allow_member_invitations`. Семантика последнего: при включённой политике участник с ролью `member` может **только создать** приглашение, и только с ролью `member` (поле роли в его форме отсутствует, сервер игнорирует/отклоняет иное); ссылка показывается один раз. Список приглашений, отзыв, ротация и приглашение администраторов по-прежнему требуют `invitations.manage`. Созданные участниками приглашения видны в админском списке с `created_by` и помечены; аудит `invitation.create` пишется одинаково. Выключение политики не отзывает уже созданные приглашения.
- Передача роли главного администратора.
- Панель прав администратора (см. «Роли и точечные права»): `PATCH /organization/members/{id}` принимает `permissions`; `GET /me` и `OrganizationMember` возвращают `permissions`.

### 7. Аудит

См. раздел «Человекочитаемый аудит»: `changes` в metadata, обогащение ответа, фильтры и курсорная пагинация, словарь описаний, тест на полноту каталога.

## Контракты и данные

- Миграции разделяются по вертикальным срезам: профиль/статус; `actor_permissions`; password/email lifecycle; audit category. `actor_permissions` хранит `org_id`, `actor_id`, `permission`, `granted_by`, `granted_at` и запрещает права для не-admin на уровне БД. Таблицы `password_reset_tokens` и `email_change_tokens` хранят только hashes; `users.must_change_password_at` фиксирует принудительную смену.
- OpenAPI: `User.title/about`, `OrganizationMember.title/last_seen_at`, `User.permissions`, `OrganizationMember.permissions`, enum `Permission`, `UpdateMeRequest`, `ChangePasswordRequest`, `TransferOwnershipRequest`, `UserPreferences` (полный, новые поля уведомлений и `snoozed_until`, без папок и закрепов), `UpdatePreferencesRequest` (частичный), `PUT /preferences/chat-folders`, `PUT /preferences/pinned-chats`, `PUT/DELETE /me/status`, `POST /push/test`, `GET /push/subscriptions`, `GET /chats/notification-overrides`, `POST /me/password`, `POST /me/email/change`, `POST /me/email/confirm`, `POST /auth/password/forgot` (публичный, всегда 202), `POST /auth/password/reset`, `POST /organization/members/{id}/password-reset` (только при SMTP, ответ не содержит token), `POST /organization/members/{id}/require-password-change`, поле `must_change_password` в `User`, `AuditEvent.changes/actor_role/target_name/category`, query-параметры `/organization/audit?category&actor_id&from&to&after_id&limit`, `GET /invitations`, `DELETE /invitations/{invitation_id}`, `POST /invitations/{invitation_id}/rotate`. Локальная CLI-команда operator recovery использует тот же password-reset service, но не публикуется в OpenAPI.
- Generated TS/Go обновляются вместе, как в 3.1.

## Критерии приёмки

- Дано desktop 1280px, когда открыта любая страница настроек, тогда видна левая навигация с текущим пунктом, контент в одну колонку и ни одна карточка не шире 680px.
- Дано phone 390px, когда открыт `/settings`, тогда показан список групп, а страницы открываются полноэкранно с Back; горизонтальной полосы вкладок нет.
- Дано участник с ролью `member`, когда он открывает настройки, тогда группа «Пространство» отсутствует в навигации, а прямой переход на `/settings/workspace/*` показывает `SettingsAccessDenied`.
- Дано `admin`, когда он пытается изменить роль `owner` или другого `admin`, тогда сервер отвечает 403, а контрол в UI disabled с подсказкой.
- Дано `admin` без `integrations.manage`, когда он открывает `/settings/infrastructure` напрямую или вызывает `PATCH /organization/infrastructure`, тогда UI показывает `SettingsAccessDenied`, а сервер отвечает 403.
- Дано `owner` выдал администратору право «Аудит», когда администратор обновляет страницу, тогда пункт «Аудит» появляется в навигации без повторного входа, а в журнале есть запись о выдаче прав.
- Дано `owner`, когда он передаёт роль, тогда после подтверждения паролем он становится `admin`, новый участник — `owner`, в аудите одна запись `organization.ownership.transfer`.
- Дано изменение названия пространства, когда администратор открывает аудит, тогда он видит «… изменил название пространства: «A» → «B»» на языке интерфейса, а не код действия.
- Дано активная, но украденная сессия без знания пароля, когда вызывается `POST /me/email/change`, тогда сервер отвечает 403 и адрес не меняется (с SMTP и без). Дано SMTP настроен и корректный пароль, когда участник подтверждает ссылку с нового адреса, тогда email изменён, старый адрес получил два письма (о запросе и о смене), остальные сессии завершены.
- Дано пользователь указал должность, когда коллега открывает список участников или кликает имя в чате, тогда должность отображается.
- Дано расписание «будние дни, 09:00–19:00» в TZ пользователя, когда сообщение приходит в субботу, тогда push не отправляется, а unread-счётчик обновляется.
- Дано пользователь нажал «Отключить уведомления → на 1 час» в одном браузере, когда ему пишут в течение этого часа, тогда push не приходит ни на одно его устройство и не доставляется позже; сообщение, отправленное после окончания часа, приходит push'ем без действий пользователя.
- Дано режим «личные сообщения и упоминания», когда в групповом чате без override приходит обычное сообщение, тогда push нет; когда приходит личное сообщение или @упоминание — push есть.
- Дано SMTP настроен и email-дайджест включён, когда пользователь неактивен в чате 15 минут, тогда разрешённые события приходят одним письмом; без VAPID и browser subscription сценарий продолжает работать, а активному пользователю письмо не отправляется.
- Дано пользователь установил статус «👽 Рисую дизайны» на 1 час, когда коллега открывает список участников, тогда видит эмодзи и текст, а через час статус исчезает у всех.
- Дано администратор нажал «Сбросить пароль» участнику, когда операция выполнена, тогда администратор видит только подтверждение «Письмо отправлено», а участник получает ссылку на свой email, задаёт новый пароль, все его прежние сессии завершаются, в аудите есть запись; повторное открытие ссылки возвращает ошибку.
- Дано у участника открыты вкладка с WebSocket и мобильная сессия, когда администратор вызывает «Потребовать смену пароля», тогда обе сессии отозваны, сокет закрыт сервером немедленно, при следующем входе со старым паролем участник видит только экран смены пароля, любые другие HTTP-запросы получают 403 `password_change_required`, попытка подключить realtime получает error-frame `password_change_required` и close `4001` без reconnect-цикла, после смены пароля доступ восстанавливается.
- Дано SMTP не настроен, когда workspace owner/admin открывает участника, тогда reset-ссылка недоступна и остаётся только «Потребовать смену пароля»; дано пароль полностью забыт, когда оператор запускает локальную CLI-команду, тогда одноразовая ссылка выводится только в терминал и операция попадает в аудит с `delivery: operator`.
- Дано SMTP не настроен, когда участник меняет свой email с верным паролем, тогда адрес меняется сразу, `email_verified_at` пуст, остальные сессии завершены, в аудите есть запись.
- Дано SMTP не настроен, когда кто-либо открывает «Забыли пароль?», тогда форма показывает «Обратитесь к администратору», не раскрывая, существует ли адрес.
- Дано медленная сеть, когда пользователь быстро меняет три поля, тогда выполняется не более двух запросов и финальное состояние сервера равно последнему вводу (unit-тест `useAutosave`).

## Проверка качества

- Vitest: `useAutosave`, `describe.ts` (каждый action из серверного каталога даёт непустую строку на RU и EN), примитивы.
- Go: матрица доступа (таблица кейсов owner / admin с каждым подмножеством прав / member × операции), тест, что каждый административный handler вызывает `authz.Require`, передача ownership, маскирование `changes` для инфраструктуры, quiet hours в выборке push.
- Playwright гоняется в двух конфигурациях: с mock SMTP и без SMTP (сброс пароля, смена email, приглашения, уведомления о правах).
- Playwright desktop + phone: навигация по всем секциям, автосохранение, смена пароля, таблица участников, фильтры аудита; визуальные снапшоты страниц профиля и уведомлений.
- Ручная проверка RU/EN и pseudo-locale на длинные должности и названия.

## Риски и открытые вопросы

- **Переименование owner → «Главный администратор»** затрагивает онбординг и приглашения; нужно пройти все места с `roleOwner`.
- **Миграция папок и закрепов** на отдельные endpoints должна пройти без потери данных: JSONB-ключи остаются на месте до проверенного переноса, а web и API обновляются одним релизом. Совместимость со старыми development-клиентами не поддерживается.
- Звуки уведомлений требуют assets и пользовательского жеста для воспроизведения в браузере — если упрёмся в ограничения autoplay, оставляем один звук и switch.
