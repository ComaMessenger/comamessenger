# Инспекция фазы 5. Агентская платформа

Дата исходной инспекции: 21 августа 2026. Цель — честная оценка того, что было реализовано по [05-agent-platform.md](05-agent-platform.md), и вход для фазы 5.1. Разделы ниже сохранены как исторический baseline; номера строк относятся к состоянию до 5.1.

## Статус после фазы 5.1 — 22 августа 2026

Фаза 5.1 закрыла найденные runtime/security/lifecycle-дефекты и превратила агентов в самостоятельную рабочую поверхность. Проверка выполнена полными Go/TypeScript-прогонами; весь Go core, включая HTTP/WebSocket E2E, проверен на настоящей PostgreSQL внутри compose-сети, а схема доведена до миграции 36.

Единственный сознательно вынесенный продуктовый вопрос — общий каталог LLM-подключений уровня пространства. Сейчас credential остаётся per-agent в подвкладке «Подключения». Общая сущность подключения затрагивает роли создателя, наследование budget/policy, ротацию и multi-provider UX, поэтому её нельзя безопасно добавить как механический перенос формы; она входит в следующий отдельный продуктовый анализ агента, который был запланирован после починки 5.1.

## Итог в трёх предложениях

Фаза закрыта формально: таблицы, ручки и чекбоксы есть, но платформа не работает как продукт — встроенный runtime при дефолтных настройках сам себя блокирует rate-limit'ом, стриминг теряет дельты после нескольких десятков provider chunks, а любой trigger-run длиннее 2 минут убивается независимо от живого heartbeat. Пользовательский слой также не закончен: агента нельзя удалить, шаблонные агенты создаются ненадёжно и после создания превращаются в один большой технический конфиг без понятного сценария настройки. Безопасность построена на доверии к runtime: он получает расшифрованный provider key, сам сообщает `confirmed` и стоимость вызова, а core не может строго enforce'ить эти ограничения. Внешнему разработчику даны OpenAPI, WebSocket-контракт и примеры, но нет полноценного Agent SDK и отдельного runtime-протокола. Архитектура разрезана «по ручкам» (6 Go-пакетов общаются через общие SQL-таблицы, `canManage` скопирован 4 раза), а не по домену, и масштабируется как «один процесс на агента».

## Что сделано хорошо

- Агент — полноценный `actor` с membership через `chat_members`; составные FK `(org_id, X)`; идемпотентность run'ов по `(agent_id, trigger_id, event_seq)` и `(trigger_id, scheduled_for)`.
- API keys хранятся хешем, default-deny scope-middleware, отзыв ключа мгновенный (DB-lookup на каждый запрос + `revokeSession` для WS).
- Claim через `SKIP LOCKED` + advisory lock — гонок не найдено.
- Provider interface в runtime не протекает vendor-объектами; MCP-секреты в отдельном AEAD-домене.
- Схемы tools на JSON Schema 2020-12 с `additionalProperties: false`.

## Продуктовая оценка: сценарий управления агентом не завершён

Это не набор визуальных шероховатостей, а отсутствие законченной продуктовой модели. Сейчас страница показывает внутреннее устройство платформы вместо ответа на три пользовательских вопроса: **что агент будет делать, где он сможет это делать и когда он будет запускаться**.

1. **Агента нельзя удалить.** В core нет `DELETE /agents/{agentID}`, в TS API нет метода удаления, в UI нет destructive action. Отключение не заменяет удаление: тестовые и ошибочно созданные агенты навсегда остаются в каталоге вместе с ключами, триггерами, runs и memberships.
2. **Шаблонные агенты создаются неатомарно.** UI сначала создаёт обычного агента, затем отдельными запросами создаёт template triggers. Ошибка на любом триггере оставляет частично настроенного агента; rollback, resume и понятного статуса «настройка не завершена» нет. После создания тип шаблона не сохраняется, поэтому дальнейшая настройка Summarizer / Q&A / Onboarding ничем не отличается от редактирования raw-конфига.
3. **Редактор отражает таблицы и API, а не пользовательскую задачу.** На одной длинной странице одновременно показаны provider/model, prompt, десять scopes, memberships, токены, tool iterations, concurrency, rate limit, triggers, usage, runs, provider credential и runtime keys. Пользователь должен понимать внутреннюю архитектуру до первого успешного ответа агента.
4. **Нет readiness-модели и безопасного первого запуска.** Можно включить агента без рабочего provider credential, подходящего runtime key или правил запуска. Нет сводки «готов / не готов», объяснения блокеров, preview доступных данных, тестового запуска и проверки результата до включения автоматических триггеров.
5. **Нет устойчивого жизненного цикла.** Нужны различимые состояния `draft → needs_setup → ready → enabled → error/paused`, а также действия duplicate, reset template и delete. Сейчас есть только boolean `enabled`, а реальные причины неработоспособности разбросаны по нескольким секциям и истории run'ов.
6. **Технические ошибки не переводятся в продуктовый язык.** Пользователь видит provider/core error codes и correlation ID, но не получает ответа «что сломано» и конкретного действия: добавить ключ, выбрать чат, разрешить передачу данных, подключить runtime или исправить расписание.
7. **Агенты ошибочно помещены внутрь общих настроек.** Это самостоятельная рабочая поверхность, которая будет расти: каталог, карточка агента, песочница, история запусков, источники и подключения. Длинная страница в Settings не даёт ни нужной информационной архитектуры, ни места для этих сценариев.

## Почему «не нравится» — структурные причины

1. **Разрез по ручкам, а не по домену.** `agent / agentconfig / agentrun / agenttool / agenttrigger / agentmemory` не имеют интерфейсов между собой и общаются через общие таблицы (`agentrun` читает `agent_mcp_servers`, `message` читает `agent_runs`, `agent` пишет `agent_checkpoints`). `canManage` продублирован 4 раза. Таблица «route → scope» — ручной парсер путей в `http/identity.go:924-979`, таблица «tool → scope» — отдельно в `executor.go:344-355`; в OpenAPI scope-требования не объявлены.
2. **Добавить tool = тронуть 4–5 мест** (`rawDefinitions`, список порядка в `Definitions()`, `switch` в `execute`, `classifyError`, `requiredAgentScope`). Нет реестра «definition + handler + scope» как единицы.
3. **Встроенные агенты не существуют как самостоятельные продуктовые модули.** Summarizer / Q&A / Onboarding — локализованные строки инструкции в UI + наборы триггеров в `agentTemplates.ts`; `description` актора используется как system instruction. RU/EN-тексты присутствуют, но сценарии DoD не закреплены E2E-тестами, template identity/version не сохраняется, а поведение шаблона после создания не отделено от custom agent.
4. **Полноценного Agent SDK нет.** `@comamessenger/core` — `private`, тянет zustand и клиентский store; `agent-runtime` — `private`, при импорте запускает `main()`. Есть OpenAPI, WebSocket v1 contract и внешние TS/Python examples (`examples/agents/*`, ~200 строк), но примеры — голые `fetch` + WebSocket: без LLM, общего tool loop, streaming helper и обработки полного runtime lifecycle. Отдельной документации agent runtime protocol (`agent.status`, `message.streaming`, `agent.run.*`, формат `run.input`, lease 5–300 с, UUID `worker_id`, 8192 байт на дельту) нет. Минимального внешнего агента собрать можно, но DoD про полноценную API/SDK-документацию закрыт преждевременно.
5. **Безопасность на доверии к runtime.** Provider key зашифрован at rest, но выдаётся runtime в расшифрованном виде; `confirmed: true` приходит от клиента, бюджет проходит через добровольный `StartProviderCall`, provenance добавляется только выбранным путём публикации. Всё, что в документе названо «enforce», на деле остаётся частично cooperative.
6. **`runtime.ts` — монолит 556 строк**: claim-loop, lease/heartbeat, контекст, provider-loop, стоимость, MCP, события, классификация ошибок; `execute()`/`runProviderLoop()` с 8–9 позиционными аргументами. Тестов runtime нет (6 тестов всего — нормализация SSE и MCP-лимиты).
7. **Тесты DoD не написаны:** permission matrix (role × membership × scope × tool), replay-идемпотентность диспетчера, reap/lease-гонки, `per_chat_concurrency`, петля двух агентов, конкурентный бюджет, 429, prompt-injection фикстуры, MCP SSRF.

## Что перепроектировать (предложение для фазы 5.1)

### Продуктовый слой: сначала понятный путь к первому полезному ответу

Целевая базовая настройка должна занимать три шага и не требовать знания scopes, tokens, leases или runtime keys:

1. **Выбрать задачу.** «Отвечать на вопросы», «Делать сводки», «Помогать новичкам» или «Свой агент». Карточка заранее показывает пример результата и способ запуска.
2. **Выбрать данные и поведение.** В каких чатах работает агент, когда отвечает, что ему разрешено делать. Разрешения показываются человеческими группами («читать сообщения», «отвечать», «читать файлы»), а безопасные scopes выводятся из выбора автоматически.
3. **Проверить и включить.** Readiness checklist, preview доступов, тестовый запрос на выбранном контексте без автоматической публикации, затем одна кнопка «Включить агента».

После создания пользователь должен попадать не в raw-конфиг, а на обзор агента: состояние, где и когда он работает, последний успешный запуск, понятная ошибка и основные действия. Настройки конкретных шаблонов должны быть предметными:

- **Сводки:** какие чаты, вручную или по расписанию, период сводки, формат и куда публиковать;
- **Ответы по истории:** источники, отвечать только по упоминанию или команде, нужны ли ссылки на источники;
- **Адаптация:** целевой чат, какие материалы использовать, кому и когда отправлять приветствие;
- **Свой агент:** инструкция, источники, правила запуска и действия — сначала простые поля, затем optional «Расширенные настройки».

«Агенты» выносятся из Settings в самостоятельный раздел основной навигации. Внутри него нужны как минимум: **Обзор/каталог**, **карточка агента**, **Песочница**, **Запуски** и **Подключения**. В Settings остаются только инфраструктурные параметры уровня пространства — подключение LLM-провайдера, глобальные лимиты и политика доступа — со ссылкой в основной раздел агентов.

Provider/model, raw scopes, token limits, concurrency, chain depth, provider rate limit, runtime keys и correlation IDs должны жить в «Расширенных настройках» или режиме разработчика. Для self-hosted owner нужен мастер подключения LLM-провайдера на уровне пространства; обычный создатель агента должен выбирать уже готовое подключение, а не вставлять секрет в каждого агента.

Обязательные lifecycle actions: **выключить, дублировать, сбросить к шаблону, удалить**. Пользовательское удаление не обязано физически стирать аудит: core должен атомарно выключить агента, отозвать его ключи и WS-сессии, остановить triggers/queued runs, убрать memberships и скрыть агента из каталога, сохранив tombstone и исторические audit/usage records по retention policy. Шаблон должен сохраняться как recipe/version, а создание агента вместе с базовыми triggers должно быть одной атомарной операцией или resumable setup workflow.

### Инженерный слой

1. **Core-side provider proxy вместо выдачи ключа.** Runtime вызывает `POST /agent-runtime/provider/chat` (stream), core сам держит секрет, резервирует бюджет, считает usage из ответа провайдера по pricing-таблице, применяет rate limit и `external_data_sharing_approved`. `runtime:execute` перестаёт означать «прочитай секрет», бюджет становится enforce-able, а provider-адаптеры переезжают в Go рядом с секретами. Runtime становится тонким: контекст + tool loop.
2. **Worker уровня организации + очередь вместо polling.** Scope `runtime:worker`, claim без фильтра по агенту (`Claim(ctx, "", …)` уже есть), пул параллельных run'ов, credential на run. Long-poll claim (20–30 с) или `LISTEN/NOTIFY`; polling и heartbeat вне rate limit; rate limit — токен-бакет в Redis/памяти, а не 3 upsert'а в Postgres. Диспатч триггеров — per-agent с изоляцией ошибок и шардированием по `hashtext(agent_id) % N`. Явные `queue_timeout` и `execution_timeout` на триггере вместо hardcoded 2 минут.
3. **Единый `Authorizer` и декларативный реестр.** Интерфейс «actor permission × key scope × membership», используемый REST, tools и runtime-ручками. `type Tool struct{ Name, Scope, Mode, Schema, Handler }` — регистрация одной строкой, автоматический каталог и классификация ошибок; scope-требования аннотируются на роуте и генерируются в OpenAPI как `x-required-scope`. Tool-вызов всегда в контексте run'а с lease token — один контракт с MCP/provider. Пакеты перегруппировать по сущности (`agentplatform/{agents,keys,runs,triggers,tools,memory}`) с явными интерфейсами.
4. **Provenance как инвариант.** Если сообщение постит actor типа `agent`, `run_id` обязателен на уровне message-сервиса (422 без него); chain depth — инвариант БД, а не договорённость. Подтверждение write-tools — серверный flow: pending tool call → карточка в чате → approve/deny человеком с правом; не флаг от клиента.
5. **Структурный trust boundary.** Пользовательский контент — отдельные content-блоки или как минимум экранирование `<`/`&`; tool-ошибки возвращаются модели как `tool_result {error}`; stop reason обрабатывается (обрезка → продолжение или пометка); budget контекста по токенам; для thread-run'ов контекст берётся через `get_thread`; `run.input` содержит тело триггерного сообщения, аргументы команды, `thread_root_id`, окно `since_last_run` для schedule.
6. **SDK и плагинная модель агента.** Публикуемый `@comamessenger/agent-sdk` (typed REST по OpenAPI, WS с resume/ack/error/`4001`, `stream()` с коалесингом дельт под лимит core) и `defineAgent({ triggers, instructions, tools, onRun(ctx) })`, где `ctx` даёт `thread()`, `command()`, `since(lastRun)`, `stream()`. Summarizer / Q&A / Onboarding становятся реальными модулями в репозитории с RU/EN инструкциями и одновременно референсными примерами. `coma-agent dev`: создать агента и ключ, поднять runtime с hot-reload, `simulate mention|command|schedule`, `MockProvider` для прогонов без LLM. `docs/protocols/agents-v1.md` с форматами событий, `run.input`, лимитами и таблицей error codes.
7. **Закрыть утечки сразу, до редизайна:** `chat_ids` только менеджеру; SSRF-фильтр и запрет `http://` для MCP; `max_completion_tokens` для OpenAI; не расшифровывать provider key ради hint (хранить hint отдельно); envelope encryption с реальным `key_version`.

Перегруппировка Go-пакетов не должна быть big-bang-целью сама по себе. Сначала вводятся `Authorizer`, декларативный tool registry и явные интерфейсы; физический перенос пакетов выполняется постепенно вместе с тестами контрактов.

## Что можно сделать быстро (hotfix-срез до 5.1)

- Poll interval 500 мс → long-poll или хотя бы вынести claim/heartbeat из rate limit.
- Коалесинг стриминга (одна дельта на 100–150 мс, `agent.status` только при смене фазы) и обработка error-фреймов в runtime.
- `timeout_at` из конфигурации триггера/агента, `reap` не трогает run с живым heartbeat до `execution_timeout`.
- Model-aware выбор `max_tokens` / `max_completion_tokens`, provider integration tests, безопасное логирование тела ошибки и обработка stop reason.
- `chat_ids` скрыть от не-менеджеров.
- `thread_root_id` и тело сообщения в `run.input`; ответ в тред.
- Экранирование `<`/`&` в user content.
- Добавить `DELETE /agents/{agentID}` как атомарный lifecycle transition: disable, revoke keys/sessions, stop triggers and pending runs, remove memberships, hide from catalog; сохранить audit tombstone и покрыть права/идемпотентность тестами.
- Сделать создание template agent атомарным или resumable; не оставлять скрытые частично созданные сущности при ошибке trigger setup.
- Добавить readiness summary и блокировать включение, пока нет обязательного provider/runtime/chat/trigger setup.
