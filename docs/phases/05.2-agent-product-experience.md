# Фаза 5.2. Продуктовый опыт агентской платформы

## Цель

Превратить технически готовую платформу 5.1 в понятный продукт, где администратор проходит путь **задача → источники → действия → запуск → проверка → публикация**, не работая со scopes, runtime keys и внутренними лимитами без явного перехода в режим для разработчиков.

## Продуктовые принципы

- Agent-first только после выбора задачи: первый экран говорит о результате для пользователя, а не о provider/runtime.
- Draft и опубликованная версия разделены. Редактирование не меняет работающего агента до публикации.
- Pause — операционное состояние опубликованной версии, а не замена публикации.
- LLM и интеграции подключаются на уровне пространства и назначаются агентам без копирования секретов.
- Песочница принадлежит конкретному агенту и показывает trace, источники, tools, approvals, стоимость и результат.
- Готовые сценарии имеют предметные формы. Raw instructions, scopes, модели и технические лимиты остаются в расширенном режиме.
- Внешний SDK-агент создаётся отдельным developer-flow и не смешивается с мастером встроенных агентов.

## Целевая информационная архитектура

Глобальный уровень:

```text
/agents                каталог и состояние агентов
/agents/connections    LLM, MCP и состояние runtime пространства
/agents/approvals      общая очередь чувствительных действий
/agents/activity       запуски всех агентов с фильтрами
```

Карточка агента:

```text
/agents/:id                    обзор, readiness и публикация
/agents/:id/behavior           задача, инструкции и формат результата
/agents/:id/knowledge          источники, чаты и разрешённые действия
/agents/:id/automations        команды, упоминания, события и расписания
/agents/:id/test               безопасная песочница и trace
/agents/:id/activity           runs, usage и диагностика
/agents/:id/settings           идентичность, ownership и destructive actions
```

Выбранный агент определяется маршрутом, а не локальным состоянием страницы. Глобальные подключения и approvals не зависят от случайно выбранной карточки.

## Workspace LLM connections

Подключение — самостоятельная сущность пространства:

- имя и provider;
- canonical или OpenAI-compatible endpoint;
- зашифрованный credential и masked hint;
- разрешённые/default models;
- health state и время последней проверки;
- владелец, дата ротации и audit trail;
- общая политика внешней передачи данных и budget defaults.

Агент хранит `llm_connection_id` и выбранную модель. Secret не копируется в agent row и никогда не возвращается в browser/runtime. Удалить используемое подключение нельзя; его можно отключить, заменить или отвязать после явного подтверждения влияния.

Per-agent provider credential остаётся только как миграционный compatibility path до перевода существующих данных в connection.

## Lifecycle и версии

Стабильная identity агента отделяется от immutable behavior version:

```text
agent
  draft_version_id
  published_version_id
  operational_status: active | paused | needs_attention

agent_version
  version
  recipe + instructions
  llm connection + model
  sources + actions + triggers
  limits + policies
  created_by + created_at
  published_at
```

- Изменение опубликованного агента создаёт или обновляет draft.
- Test runs используют draft version и никогда не публикуют durable message.
- Publish атомарно валидирует readiness, фиксирует immutable version и переключает triggers.
- Rollback создаёт новый draft из выбранной опубликованной версии; история не переписывается.
- Pause немедленно запрещает новые runs, не удаляя опубликованную конфигурацию.

## Новый мастер

### 1. Задача

- Summarizer;
- Q&A по истории и файлам;
- Onboarding;
- свой встроенный агент;
- отдельное действие «Подключить внешнего агента».

Имя предлагается автоматически, handle генерируется и скрыт в обычном режиме.

### 2. Источники и место результата

Чтение и публикация задаются отдельно. Список поддерживает поиск и явно показывает приватность выбранных чатов.

### 3. Запуск

Предметная форма вместо raw trigger config: упоминание, команда, расписание с timezone, событие пространства или только ручной запуск.

### 4. Подключение и политика

Используется default connection пространства либо выбирается другое разрешённое подключение. При отсутствии подключения draft сохраняется, а владельцу показывается конкретное действие для администратора.

### 5. Review

Человеческая сводка: что агент читает, что может записывать, куда отправляет данные, когда запускается, какие действия требуют подтверждения и какой установлен бюджет.

После создания пользователь попадает в `/agents/:id/test`, а не в технический редактор.

## Предметные формы

### Summarizer

- источники и destination;
- chat/thread scope;
- вручную, по команде или по расписанию;
- since-last-digest либо выбранный период;
- секции: решения, вопросы, задачи, владельцы;
- citations и timezone.

### Q&A

- knowledge chats/files;
- места ответа;
- mention/manual trigger;
- обязательность citations;
- fallback при отсутствии подтверждённого ответа;
- возможность эскалации человеку.

### Onboarding

- событие вступления и задержка;
- destination или direct message;
- knowledge sources;
- приветствие, тон и suggested questions;
- контакт/чат эскалации.

## Test Studio

Test Studio запускает draft version в режиме `dry_run`:

- durable messages и внешние write tools не исполняются;
- предполагаемые writes показываются как preview;
- read tools работают с реальными правами агента;
- trace показывает этапы, tools, источники, citations, latency, tokens и estimated cost;
- можно начать новую сессию и повторить тест после изменения draft;
- шаблоны поставляют 3–5 готовых тест-кейсов и ожидаемые свойства результата.

## Роли

- `agents.build` — создавать, редактировать и тестировать drafts;
- `agents.publish` — публиковать, pause/resume и rollback;
- `agents.approve` — принимать чувствительные действия;
- `integrations.manage` — создавать и ротировать workspace connections;
- `agents.observe` — activity, usage и diagnostics без изменения конфигурации.

Owner сохраняет все возможности. Старый `agents.manage` временно раскрывается в новые разрешения для обратной совместимости.

## Метрики и критерии приёмки

- При готовом workspace connection Summarizer создаётся, проверяется и публикуется за 3–5 минут.
- Обычный путь не показывает scopes, runtime key, token limit или correlation ID.
- Изменение draft не влияет на опубликованного агента до Publish.
- Невозможно опубликовать agent version без connection, источника, trigger policy и успешного readiness check.
- Test Studio не создаёт durable messages и не исполняет внешние writes.
- Ротация workspace credential не требует изменения или перезапуска агентов.
- Любой run содержит agent version, connection и correlation provenance.
- Все product actions и sensitive connection changes отражаются в audit log.
