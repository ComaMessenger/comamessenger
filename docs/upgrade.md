# Обновление и откат Coma

Для установок из готовых образов ([docs/install.md](install.md)). Стейджинг Coma собирается из исходников и обновляется по-другому, см. [deployment-test-server.md](deployment-test-server.md).

## Версии

Версия записывается как `MAJOR.MINOR.PATCH`, например `0.2.1`. Предварительные версии вида `0.2.0-rc.1` подходят для пробы, на рабочем сервере их не ставят.

- Образы публикуются в `ghcr.io/comamessenger/coma-core`, `coma-web` и `coma-agent-runtime` под тегом версии. Опубликованную версию не перезаписывают. В `compose.yaml` каждого выпуска образы закреплены по digest, поэтому один и тот же `compose.yaml` всегда запускает одни и те же образы.
- В заметках к выпуску на [странице выпусков](https://github.com/ComaMessenger/comamessenger/releases) указано, что изменилось и нужны ли перед обновлением какие-то действия.
- Обновляться можно с любой версии на любую более новую. Миграции базы применяются по порядку при запуске Core.

## Обновление

```sh
cd /opt/coma
./upgrade.sh 0.2.0
```

Что делает скрипт:

1. Скачивает `coma-deploy-0.2.0.tar.gz` и `SHA256SUMS` со страницы выпуска и сверяет контрольную сумму.
2. Делает резервную копию через `./backup.sh`. Если копия не получилась, обновление не начинается и ничего не меняется.
3. Кладёт файлы текущей версии в `releases/<текущая версия>/`.
4. Заменяет `compose.yaml`, `Caddyfile` и скрипты на новые и пишет новую версию в `COMA_VERSION`. Остальной `.env` не меняется.
5. Выполняет `docker compose pull`, затем `docker compose up -d --wait`. При первом запуске Core применяет новые миграции.

Пока идёт перезапуск, Coma недоступна от нескольких секунд до минуты. Клиенты переподключаются сами и дополучают пропущенные сообщения.

### Вручную

Если скрипт использовать нельзя, например у сервера нет доступа к GitHub, повторите те же шаги руками:

```sh
cd /opt/coma
./backup.sh                                   # обязательно: без копии отката нет
mkdir -p releases/0.1.0 && cp compose.yaml Caddyfile *.sh *.example releases/0.1.0/
tar xzf ~/coma-deploy-0.2.0.tar.gz --strip-components 1 --exclude .env
sed -i 's/^COMA_VERSION=.*/COMA_VERSION=0.2.0/' .env
docker compose pull
docker compose up -d --wait
```

Обновлять образы автоматически, например через Watchtower, не стоит. Обновление меняет схему базы, поэтому перед ним нужна свежая копия и время, чтобы проверить результат.

## Откат

Сначала проверьте, менялась ли схема базы. Если между версиями миграций не было, откат проходит как обычное обновление:

```sh
./upgrade.sh --rollback 0.1.0
```

Скрипт берёт файлы из `releases/0.1.0/`, а если их нет, скачивает с GitHub.

Если новая версия уже обновила схему базы, старый Core на ней не запустится. В журнале будет:

```
Coma 0.1.0 cannot start: database connection and migration failed.
  database schema is newer than this Core: the database is at migration 70, this Core knows migrations up to 64
```

Так Core защищает данные: старый код не умеет работать с новой схемой и может их испортить, а автоматического отката миграций в Coma нет. Есть два выхода:

- вернуться на новую версию: `./upgrade.sh 0.2.0`;
- восстановить копию, которую `upgrade.sh` сделал перед обновлением: `./restore.sh backups/coma-<дата>-0.1.0.tar`. Сообщения и файлы, появившиеся после обновления, при этом пропадут.

## Если новая версия не запустилась

`upgrade.sh` показывает последние строки журнала Core и подсказывает команду отката. Порядок действий:

1. Прочитайте абзац `Coma … cannot start`: в нём причина и подсказка.
2. Если причина в настройках (например, новая версия требует переменную, о которой написано в заметках к выпуску), исправьте `.env` и выполните `docker compose up -d --wait`.
3. Если причину быстро найти не удаётся, откатитесь, как описано выше, и [напишите нам](https://github.com/ComaMessenger/comamessenger/issues), приложив журнал `docker compose logs core --tail 200`. Секретов в нём нет.
