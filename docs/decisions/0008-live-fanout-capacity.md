# ADR-0008: batch hydration и in-memory live fan-out

- Статус: принято и реализовано
- Дата: 2026-08-19

## Контекст

Первый профиль фазы 2.5 открыл 2 000 WebSocket и закоммитил 200 сообщений за секунду, но за следующие 20 секунд доставил только 83,83% из 400 000 кадров; p95 live delivery составил 18,369 с. Каждая сессия независимо вызывала `eventlog.Store.Replay` при продвижении watermark. Одни и те же события и message payload гидратировались до 2 000 раз, а PostgreSQL pool 10/10 становился очередью без lock contention.

Узкое место находилось не в Redis wake-up и не в последовательности `organizations.event_seq`, поэтому Redis Streams, Kafka, увеличение DB pool и горизонтальное размножение того же алгоритма проблему не решали.

## Решение

Durable live path разделён на общий push и индивидуальное восстановление:

1. Dispatcher один раз на организацию читает `(old_watermark, current_watermark]` батчами не более 256 событий.
2. `eventlog.Store.Live` в одном PostgreSQL statement гидратирует payload и вычисляет актуальных active recipients через `actors`, `chat_members` и состояние chat. Actor-only audience и `exclude_session_id` сохраняются.
3. Каждый event сериализуется в immutable JSON один раз. Hub раздаёт те же bytes только локальным сессиям разрешённых actors.
4. У каждой сессии остаётся bounded очередь по числу событий и байтам. Переполнение закрывает соединение с `4008`; клиент восстанавливается через durable `Replay(last_seq)`.
5. `Replay` остаётся единственным путём для initial backlog, reconnect и resume. ACK, retention и wire protocol не меняются.
6. Записи в сокеты ограничены общим `WS_MAX_CONCURRENT_WRITES` (default 8). Это ограничивает burst системных write calls и не даёт 2 000 соединениям одновременно исчерпать socket buffers хоста.

Целевой инвариант: PostgreSQL hydration выполняется один раз на event batch, а работа на локального получателя ограничена проверкой map, bounded enqueue и записью уже подготовленных bytes. Membership cache намеренно не добавлен: текущая проверка в SQL проще и сохраняет корректность. Кэш допустим только как отдельная оптимизация с invalidation из упорядоченного durable log и доказанным benchmark эффектом.

## Корректность при гонках и отказах

- Регистрация сессии не двигает общий watermark организации вперёд: старое соединение не может потерять промежуточный event из-за нового соединения.
- Event, попавший одновременно в backlog и live queue, дедуплицируется по `seq` в session loop.
- Потерянный Redis Pub/Sub hint восстанавливается настраиваемым PostgreSQL polling; повторный hint безопасен.
- Revoke/expiry отменяет контекст подписки независимо от состояния очереди.
- Медленный клиент не удерживает неограниченную память и возвращается по `last_seq`.

## Измеренный результат

На той же машине и том же профиле после изменения доставлены 400 000 из 400 000 кадров без отключений. p95 уменьшился с 18,369 до 1,532 с, wall time прогона — с 29,29 до 10,66 с, PostgreSQL snapshot CPU — со 151,9% до 34,2%. DB pool кратковременно достиг 10 соединений во время конкурентных command transactions, но после прогона содержал 5 соединений; dispatcher прочитал 200 событий в 13 bounded batches.

Это подтверждает снятие множителя «сессии × hydration». p95 всё ещё включает физическую запись 400 000 WebSocket frames на одном процессе и loopback host; улучшение ниже секунды возможно отдельной оптимизацией socket scheduling или бинарного wire format, но не является correctness-блокером фазы 2.
