# ADR-0010: надёжная доставка Web Push

- Статус: принято
- Дата: 2026-08-19

## Контекст

Web Push является побочным каналом уведомления, а не частью durable WebSocket delivery. Отправка напрямую из HTTP handler или Redis Pub/Sub потеряется при рестарте и не даст контролировать повтор, настройки пользователя и недействительные browser subscriptions.

## Решение

`message.created` в той же PostgreSQL-транзакции создаёт уникальную `notification_job` для durable event. Worker короткими батчами материализует доставки на актуальные subscriptions и затем атомарно забирает их через `FOR UPDATE SKIP LOCKED` и ограниченный lease. Уникальность `(org_id, event_seq, subscription_id)` защищает материализацию от повторов, lease — от одновременной отправки двумя репликами и допускает восстановление после падения worker.

Перед материализацией проверяются membership, глобальный `push_enabled`, `notify_level`, mute и mentions. Непосредственно перед отправкой active-screen lease из realtime hub может подавить push открытого чата; Redis и lease остаются только оптимизацией и не влияют на сохранность события.

- успешный ответ провайдера завершает delivery;
- `404`/`410` удаляют недействительную subscription;
- временные ошибки повторяются с ограниченным exponential backoff;
- payload по умолчанию содержит автора, чат и deep link, но не текст сообщения;
- текст включается только настройкой `push_preview`;
- VAPID private key хранится только в server environment, public key доступен клиенту через capability endpoint.

Browser permission запрашивается только после явного действия пользователя. Service worker открывает существующее окно либо создаёт новое по deep link. Отказ или отсутствие Push API не блокируют мессенджер.

## Последствия

Push переживает рестарты Core и не дублируется при повторной материализации. PostgreSQL остаётся источником истины, а будущая замена транспорта очереди требует бенчмарка и не меняет клиентский контракт.
