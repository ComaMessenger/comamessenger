# Авторизация — чего не хватает под новый дизайн

Экраны 03–08 из канваса «Авторизация» реализованы в `apps/web/src/auth/`. Ниже — то, что дизайн показывает, а API/продукт пока не даёт.

## Приглашение: карточка «кто и куда приглашает»
- **Дизайн:** блок с аватаром и текстом «Ольга Верёвкина приглашает вас в пространство Северный офис как участника», внизу «Приглашение для maxim@severny.ru · действует до 12 сентября».
- **Сейчас:** нет эндпоинта для чтения приглашения по токену; данные видны только после `POST /invitations/{token}/accept`. Карточка не рендерится.
- **Что нужно:** `GET /api/v1/invitations/{token}` (публичный, без сессии): имя/аватар пригласившего, название пространства, роль, email получателя, `expires_at`, статус (`valid` / `expired` / `revoked` / `used`).

## Приглашение: состояние «Аккаунт уже создан»
- **Дизайн:** отдельный экран с «Войти как maxim@severny.ru» / «Это не я».
- **Сейчас:** сервер отвечает общей ошибкой; клиент не отличает «использовано» от «истекло» и показывает один экран «Приглашение недействительно».
- **Что нужно:** различимый код ошибки (`invitation_used` с email/handle) или статус из эндпоинта выше.

## Приглашение: подсказки свободных handle
- **Дизайн:** «Handle уже занят. Свободно: @maxim, @m.kal».
- **Сейчас:** 409 без вариантов; показываем только «Handle уже занят».
- **Что нужно:** в ответе 409 (или отдельный `GET /handles/suggest?base=…`) список свободных вариантов.

## Восстановление: точный статус токена
- **Дизайн:** «Ссылка устарела или уже использована» отдельно от прочих ошибок и до отправки формы.
- **Сейчас:** токен не проверяется до `POST /auth/password/reset`; любая 4xx на отправке трактуется как истёкшая ссылка.
- **Что нужно:** `GET /auth/password/reset?token=…` (валидность + email/пространство для lead «Для lev@severny.ru · Северный офис»).

## Восстановление: email в заголовке экрана «Новый пароль»
- **Дизайн:** lead «Для lev@severny.ru · Северный офис».
- **Сейчас:** email неизвестен до отправки; показываем только название пространства из branding.
- **Что нужно:** см. предыдущий пункт.

## Политика паролей
- **Дизайн:** индикатор «6 из 10 символов» → «Надёжный».
- **Сейчас:** единственное правило — минимум 10 символов; индикатор считает только длину.
- **Что нужно:** если появится серверная политика (сложность, запрет утёкших паролей), отдать её в `PublicBranding`/bootstrap status, чтобы клиент валидировал одинаково.

## Bootstrap: подсказки по slug/handle с сервера
- **Дизайн:** «Предложение: severny-office», галочка «handle свободен».
- **Сейчас:** slug нормализуется на клиенте (`suggestSlug`), handle проверяется только регуляркой; уникальность неизвестна до отправки.
- **Что нужно:** необязательно; при желании — `GET /bootstrap/check?slug=&handle=`.

## Bootstrap: маскирование токена
- **Дизайн:** `cm_bt_4f9a••••7e21` — показывает начало и конец.
- **Сейчас:** обычное поле пароля с кнопкой «показать».
- **Что нужно:** ничего со стороны API; частичное маскирование можно добавить в UI позже.

## Загрузка: статус сервера
- **Дизайн:** «Сервер отвечает дольше обычного…» как реальный статус.
- **Сейчас:** текст показывается по таймеру 8 с, а не по ответу health-эндпоинта.
- **Что нужно:** лёгкий `GET /healthz` с таймингами или использовать `bootstrapStatus` с таймаутом; тогда текст можно привязать к реальному состоянию.

## Мелочи
- Версия в подвале («v2.14»): в `PublicBranding` нет версии сервера — подвал показывает только «Coma Messenger · self-hosted». Нужно поле `server_version`.
- Автозаполнение браузера (серый фон полей) стилизуется через `:-webkit-autofill` в `ui.css`; Firefox использует свой цвет.
